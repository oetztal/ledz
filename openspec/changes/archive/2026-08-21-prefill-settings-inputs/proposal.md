## Why

The settings page is inconsistently prefilled. `gammaMode`, `cycleTime`, `touchEnabled` and `touchThreshold` load their current values into the control; `deviceName`, `numPixels`, `ledPin` and `wifiSSID` render empty with a placeholder, and instead echo the saved value in a read-only `info-box` below the button.

The result is that a user who wants to change the LED count from 300 to 240 has to read the number out of the info box, then type both digits into an empty field — the form does not show what it is editing. The empty-field convention also overloads "blank" to mean "leave unchanged", which is invisible in the UI and produces confirmation dialogs that describe a partial update.

Every value needed to prefill these fields is already served by `/api/status`, except the configured WiFi SSID.

## What Changes

- **All editable settings inputs are prefilled** from the device's current values on page load: `deviceName`, `numPixels`, `ledPin`, `wifiSSID`, alongside the four controls that already do this.
- **Change detection moves from "is the field empty" to "does the field differ from the loaded value".** The page keeps a snapshot of the loaded settings and submits only fields the user actually changed. The confirmation dialog lists real changes, not every field.
- **Redundant `Current: …` echoes are removed** and replaced by a per-section *modified* indicator that names the saved value the user is editing away from. This preserves the one thing prefill would otherwise destroy: the ability to see what is stored after you have typed over it.
- **`/api/status` gains `wifi_configured_ssid`**, read unconditionally from `Config::WiFiConfig::ssid`. The existing `wifi_ssid` key (the *connected* network, present only when `WL_CONNECTED`) is unchanged, so `about.html` and `control.html` keep working.
- **`POST /api/settings/wifi` preserves the stored password when the `password` key is absent.** Prefilling the SSID without the password creates a one-click credential wipe; omitting the key on a blank field closes it. A "Open network (no password)" checkbox provides the explicit way to clear it.
- **Clearing a prefilled field is a validation error, not a no-op.** With prefill, a blank `numPixels` is a user mistake rather than a signal.

## Capabilities

### New Capabilities
- `settings-page`: Describes the device settings web UI — how each editable control is populated from current device state, how modified fields are detected and submitted, and how WiFi credentials are handled when the password cannot be prefilled.

### Modified Capabilities
- *(none — no existing spec covers the settings page or the settings HTTP API)*

## Impact

- `data/settings.html` — prefill `deviceName`/`numPixels`/`ledPin`/`wifiSSID`; add a `savedSettings` snapshot and a `diff`-based submit path in `updateHardwareSettings()`, `updateDeviceName()` and `updateWiFi()`; replace the value spans in the three `info-box` elements with modified indicators; add the open-network checkbox
- `src/WebServerManager.cpp` — add `wifi_configured_ssid` to `GET /api/status`; change `POST /api/settings/wifi` to load the existing `WiFiConfig` and only overwrite `password` when the key is present
- `src/generated/settings_gz.h` — regenerated by `scripts/compress_web.py` during the PlatformIO pre-build step
- `test/` — coverage for the WiFi password-preservation branch

Backward compatible for the UI. One deliberate API behavior change: a client that previously POSTed `{"ssid":"x"}` to `/api/settings/wifi` had the password silently cleared; it will now be preserved. The AP-mode setup endpoint `POST /api/wifi` (`handleWiFiConfig`) is a separate handler and is not touched — first-time setup still starts from an empty form.
