## Why

The Wave show is the only multi-variant show on the control page whose parameter section exposes only raw numeric inputs. Every other show with named parameter sets — Mandelbrot, ColorRanges — already has a one-click way to load a curated configuration from the gallery definition in `scripts/show_variants.json`. `show_variants.json` defines three named Wave variants (`default`, `tight`, `calm`), but the device firmware has no knowledge of them; the file is consumed only by `scripts/build_pages.py` to render preview PNGs.

A user picking `tight` today has to read the JSON file, remember the numbers (`decay_rate: 4.0, brightness_frequency: 0.4`), and type them into the inputs. A `Preset` dropdown sitting above the existing numeric inputs — mirroring the Mandelbrot pattern at `data/control.html:80-91` — closes that gap and makes the existing gallery definitions usable from the device.

## What Changes

- Add a `Preset` `<select>` dropdown to the Wave parameter section in `data/control.html`, populated with the three variants from `scripts/show_variants.json` (`Default bounce`, `Tight fast`, `Calm broad`).
- Selecting a preset populates the `Decay Rate` and `Brightness Frequency` inputs with the variant's values and resets `Mode` to `bounce`. The user still clicks `Apply Parameters` to send the values to the device.
- The `Default bounce` entry is labelled `Default bounce (no change)` so the user understands its selection is a no-op against the existing input defaults.
- After the server echoes the applied params on the next 10 s status poll, `populateShowParams()` resets the preset dropdown to `-- select a preset --` so the numeric inputs and the dropdown don't disagree while the user edits.
- No C++ changes. No new endpoints. No new NVS keys. No change to `TouchController.cpp` — the touch button keeps cycling its single `{}` variant.
- After editing, `scripts/compress_web.py` (PlatformIO pre-build hook) regenerates `src/generated/control_gz.h` from `data/control.html` automatically.

## Capabilities

### Modified Capabilities

- `wave-show`: The `Web UI exposes the Wave parameters` requirement is extended so the Wave parameter section includes a `Preset` dropdown above the existing `Mode`, `Decay Rate`, and `Brightness Frequency` controls. Selecting a preset fills the `Decay Rate` and `Brightness Frequency` inputs with the variant's `decay_rate` and `brightness_frequency` values and resets `Mode` to `bounce`. The dropdown lists the three variants `default`, `tight`, and `calm` from `scripts/show_variants.json`. The `POST /api/show` payload, NVS persistence, and Wave C++ contract are unchanged.

## Out of Scope

- Touch-button cycling (`WAVE_VARIANTS` in `src/TouchController.cpp:45`) — the user explicitly scoped this change to the web UI; the touch button stays at one variant.
- Single source of truth for the three variant numbers — they remain duplicated between `scripts/show_variants.json` (consumed by `build_pages.py`) and the JS `wavePresets` object (consumed by the device). The Mandelbrot preset dropdown follows the same duplication; consolidating would be a separate change.
- The `mode` parameter — all three variants set `mode: "bounce"`, and `mode` is currently a documented no-op (`bounce` and `traveling` render identically). When/if `mode` becomes meaningful, the preset handler already resets it to `bounce`.
- Emoji / icon vocabulary for the dropdown labels — using 🌊 / ⚡ / 💤 follows the Mandelbrot / ColorRanges convention but is purely cosmetic.
